# Живое сравнение discovery и всех схем

Дата клиента: 19 октября 2026, Asia/Tomsk. Стенды находятся отдельно от рабочих
БД: `/srv/storage/butler/agents/tool-discovery-native-20261019` и
`/srv/storage/butler/agents/tool-discovery-cost-pair-20261019` на `ssh laba`.
Использованы настоящие Go Orchestrator/Broker, PostgreSQL, Doctor runtime и
Antigravity / `gemini-3.8-flash-high`, output ceiling 32768, timeout 300 s.
Модель не скриптовая; runtime действительно обращается к диагностике своего Core.

## Проверяемая цепочка

[Полные безопасные наблюдения](../../deploy/tool-discovery/native-comparison-20261019.json)
содержат точные run/tool/operation IDs, аргументы search/load, refs, времена,
реальные ответы диагностики, числовой usage и подтверждённые effect receipts.
В отдельно разрешённой паре deferred-вызовы идут строго в таком порядке:

1. `tools.search` — поиск диагностики контейнеров.
2. `tools.load` — загрузка точного найденного contract ref.
3. `doctor.check_container` — настоящий вызов runtime; `container.orchestrator`
   и `container.tool-broker` независимо возвращают `healthy`.
4. Модель выдаёт ответ, соответствующий наблюдению.

Все три вызова завершены, их effects имеют `effect_confirmed`. До поиска
переданы только две discovery-схемы; после load activity показывает добавленную
схему Doctor. В eager-режиме переданы **все 44 доступных этому run контракта**,
а не искусственный набор заглушек. Общий установленный каталог шире: текущие
полномочия фильтруют его одинаково для обоих режимов. Discovery-контроли —
разница экспериментальных режимов, а не расширение исполнительных полномочий.
Сохранённый verdict финала остаётся `unverified`; независимая проверка выше
относится к этому конкретному заданию и receipts.

## Полный token usage и задержка одной фиксированной пары

Одинаковый запрос: проверить состояние контейнера orchestrator без изменений.
Одинаковые модель, инструкции приложения, доступные операции, лимиты, новый
пустой session context и версия сервисного кода. Дополнительные инструкции
discovery являются частью исследуемого режима. Без fallback и скрытых повторов.

Подгрузка уменьшила полный token usage этой пары на **15,54%**, увеличив время
в **2,14 раза**. Начальные schema bytes уменьшились на 95,40%, но это не размер
нативного HTTP-запроса и не оценка тарифицируемых токенов.

Денежная **полная стоимость неизвестна**: провайдер не предоставляет расход
подписки/счёт на каждый запрос, стоимость хоста и энергии не измерена.
`subscription_no_overage` — основание операторского допуска, а не доказательство
бесплатности. Даже token total не подменяет денежный счёт. Здесь учтены все
шесть запросов обоих run, включая search/load и финальные ответы; unknown usage
в этой отдельной паре — 0. Проведено 6 из разрешённых максимум 8 запросов.

## Качество и сохранённые неудачи

Предварительно зафиксированы четыре русскоязычных задания: PostgreSQL/Redis,
контейнеры, конфигурация провайдера с оговоркой о генерации и арифметика без
тулзов. В полном preliminary V4: eager **4/4**, deferred **3/4**. В deferred
provider-задании после успешных диагностик получен `invalid_tool_request`.
Эта неудача не удалена и не заменена результатом последующего удачного опыта.
**Неухудшение качества не доказано.** Четыре разных задания и одна полная
стоимостная пара не устанавливают качество на произвольных рабочих сценариях.

Следующее окно V5 содержит удачные первые две пары и четыре остановки по
`budget_active_millis_owner_day`. Они не считаются успешными ответами модели.
После явного разрешения владельца создано отдельное окно только одной пары,
с максимумом 8 дополнительных запросов и сохранением предыдущей истории.

Итого: 38 модельных admissions в первом стенде + 6 в разрешённой паре = **44**.
В первом стенде один admission имеет неизвестный input/output, полный total
неизвестен для 35 admissions. Их reservations, БД, markers и неудачи сохранены.
Суммарная стоимость всех окон поэтому остаётся неизвестной; новый учёт не
восстанавливает потерянные исторические измерения и не обнуляет расходы.

Нулевые preparations с несовместимым dynamic binary/Alpine, пустым новым
manifest и неправильным private hostname сохранены отдельно. Первый provider
admission остановился при OAuth через старый proxy. Read-only HEAD-проверка
подтвердила прямой OAuth-маршрут; в последующих frozen-парах только OAuth
обходит proxy, генерация использует один и тот же Cloud Code маршрут.

## Изменения и проверки

Для сохранения thinking consumption бюджетная обёртка записывает один безопасный
числовой `model turn usage observed` log на полный ответ. Текст, reasoning,
provider frames и credentials в него не попадают. Collector сохраняет записи
до пересоздания контейнера и связывает их с durable admission IDs.

При совместном включении production-фич обнаружена отдельная ошибка композиции:
`skills.RoutedExecutor.Next` был привязан к router и пропускал discovery.
Обёртка теперь сохраняет предыдущий executor; actual Broker/Core integration
проверяется и без skills, и с skills. Это не меняет native schema/transport/
selection-код измеренной пары. Candidate private client также согласован с
точным Docker Compose endpoint; похожие хосты/порты и произвольный HTTP запрещены.

В рабочем мобильном сценарии доказан и устранён прежний сбой: модель выбирала
`semantic_hybrid` из canonical memory.search schema при отсутствующем adaptive
reader, после чего owning service запрещал чтение. Core теперь показывает только
`catalog_exact`, без event-date filters, пока соответствующая композиция не
существует. Canonical contract/ref и отказ owning service не изменены. Эти memory
методы не входили в44 доступных контракта стоимостной пары; её измерения сохраняют
свой исходный scope, а не выдаются за сравнение всего нового production workload.

`tool-discovery-local.ps1` повторно проверяет изолированный PostgreSQL,
actual Broker, обычный Input/Core, recovery, contracts и transports с race/vet.
Итог:24 проверки,0 fail/skip, затем успешный vet; exact имена/времена/hash
сохранены в [manifest](../../deploy/tool-discovery/post-rollout-verification-20261019.json).
Candidate control отдельно проверен Linux/race и Windows. Основной checkout
не изменён. Нативные стенды после сохранения доказательств останавливаются,
постоянные данные и учёт остаются. Production opt-in и его ограничения описаны
в [отчёте переноса](../operations/laba-main-20261019.md).
