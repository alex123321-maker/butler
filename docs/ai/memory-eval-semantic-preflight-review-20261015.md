Дата: 2026-10-15. Рецензент — отдельный модельный агент
`/root/memory_independent_review`; автор набора и реализации — `/root`.

**RUBRIC_AND_CALIBRATION_ALLOWED_ONLY. NATIVE_ENTRY_WITHHELD.**
Все 12 исправленных сценариев и все 10 калибровочных примеров прочитаны.
Разметка допускается для будущего ограниченного диагностического запуска;
это не готовность исполняемого runner и не разрешение на inference.
Исходниковый gate требует закрытия перечисленных ниже конкретных замечаний,
точного test proof и отдельной сверки подготовленных source/binary/runtime pins.

| f04 | f04s1/r1 и f04s2/r1 совместно задают Северную тропу и IR-7042 для одного Ирис-72. Оба звена есть в oracle; Ирис-73 — другая посылка. |

| f06 | Обычная среда начинается в 10:00 по f06s1/r1. f06s2/r1 ограничивает 12:30 одной фестивальной датой и явно возвращает обычное расписание. |

| f08 | Два противоречащих окончательных значения имеют одинаковое время; f08s2/r1 явно сообщает неизвестность порядка и отмены. Выбрать одну сумму как бесспорную нельзя. Слово «первой» не пересиливает прямое указание неизвестного порядка. |
| f09 | f09s1 — tombstone без тела, f09s2/r1 сообщает удаление и запрет восстановления из производных. Допустимого номера в корпусе нет. Oracle не содержит удалённого тела. |
| f10 | f10s2/r1 фиксирует терракотовую обложку Можжевельника. Синий Тополь и непринятое зелёное предложение гостя не заменяют выбор хозяина. |

| f12 | Три отдельных источника одной Пихты-88 задают адрес Мастеров,17, код PF-6281 и часы09:30–18:30. Все три необходимы для полного ответа и включены в oracle. Пихта-89 не подходит. |

Во всех случаях оригиналы публичны, даты не позже as_of, роли и
идентичность сущностей различимы. Ответ в ordinary language допускается:
строкового совпадения с required_facts, конкретного числа цитат,
канонического abstain или action enum не требуется. F07/f08/f09
действительно не дают запрошенного определённого факта; корректное
объяснение неопределённости здесь может быть полным.

Предъявлено 38 native inputs: 12 × 3 основных arms плюс два
retrieval_repeat для f01 и f08. Это повтор ответа при идентичном
зафиксированном retrieval context. Текущая сборка inputs использует тот же
capture; эти два повтора не доказывают воспроизводимость второго поиска,
запроса embedding или независимого индексирования. Обычный retrieval
сравнивается с заранее достаточным oracle, а не со случайно более длинным
full_context.

Сценарии новые относительно переоценённых v2 originals, но публичные,
короткие и синтетические. Автор мог видеть предыдущие результаты.
Проверка фиксирует факты и правила до будущих ответов; она не создаёт
приватного слепого бенчмарка и не доказывает обобщение на весь продукт.

сущности, cal06 использует отменённый адрес. Это содержательные ошибки.

запрошенных фактов и corpus-correct, однако ungrounded/context-incorrect;
primary correct им не присвоен.

Cal07 обоснованно объясняет отсутствие подтверждённого времени.
Cal08 без основания не сообщает доступный код при правильном курьере,
поэтому partial даже по context. Cal09 безопасно отказывается при пустом
context, но весь разрешённый корпус содержит ответ, поэтому practically
partial. Нельзя смешивать cal08 и cal09 с выдуманным фактом или с полным
успехом вопроса.

Автор сообщил о совпадении с заранее записанным ключом: 10/10 классов и
40/40 четырёх основных измерений. Рецензент ключ не открывал; этот факт
сопоставления является сообщением автора, не отдельной слепой проверкой
содержимого ключа. Оценки не изменялись после этого сообщения. Десять
авторских примеров не дают универсальной оценки точности рецензента.

## Исходниковая готовность пока удержана

Прочитан рабочий diff semantic collector/schema/scorer/launcher.
В model projection отсутствуют required_facts, forbidden_claims,
oracle_source_ids, split/review labels. Выбор достаточных oracle источников
является намеренным условием arm, а их содержимое остаётся обычными
оригиналами. Legacy answer envelope сохранён отдельной веткой; новый
free answer не получает оценки по старому каноническому строковому списку.

В первой просмотренной версии обнаружены конкретные операционные пробелы:

1. Seal/measurements/export defer регистрировался после read captures и
   native factory. Ошибки до него могли оставить потраченный write/read/
   auth prefix без финальной проекции. Удержание должно охватывать все
   стадии spend; успешный writer передаёт открытое окно read, ошибки
   закрывают его и сохраняют расходы/ledger.
2. Shell записывал actual runtime proof, но Go не проверял его до чтения
   local token/native import/key. Нужна независимая проверяемая привязка
   image, command, UID, лимитов, RO mounts, networks и proxy/local bypass
   перед private backend/auth.
3. Первоначальные 3h/185m были короче 38 × 5m. Автор сообщил об исправлении
   на finite 4h/245m; точные source bytes и timeout/cleanup проверяются
   отдельно до admission. Deadline не должен меняться после старта.
4. Projection unit не покрывал полноценный lifecycle нового entry.
   Требуется отдельный fake backend/native PG proof реального
   write → writer exit → restart → new reader, сохранения failed prefix,
   отсутствия повторов и полного planned denominator.
5. Retrieval_repeat использует общий capture. Pipeline latency должна
   учитывать эту общность последовательно и не превращать shared read
   в два фактических расхода.

Автор исправляет эти пункты. Этот документ фиксирует **разрешение
методики и разметки**, а не выдаёт опережающий PASS ещё не проверенному
исправленному executable. Отдельное source/test readiness и затем actual
prepared/runtime gate должны явно назвать точные hashes и конечный
лимит вызовов. Исторические окна не переоткрываются, failed outputs не
заменяются, старый бюджет не используется как новое разрешение.

Независимый модельный рецензент может ошибаться. После сбора необходима
проверка самих originals, фактически видимого текста, расходов, SQL и
полного знаменателя; отрицательные или недоступные ответы сохраняются.
Полноценный долговременный task effect и вся transcript/profile/consolidation
архитектура этим документным контуром не доказаны.
