# Exact action authorization

A new explicit one-use login vault consent can waive a duplicate action approval
only for the exact `browser.login` revision1 protocol and two matching deferred
request references. Input claim, current task/mandate tools/resources/commit
effect, denials, account revision, expiry and final dispatch checks still apply.
Legacy preparation consent cannot authorize it; generic click/POST approval is
unchanged. The durable dispatch transaction also pins the owning login Input.
See [bounded login](browser-login-protocol.md).

The kernel's optional post-effect `browser.freeze_snapshot` probe receives its
own ordinary read intent/grant and budget charge. It carries only the original
browser session ID, checks current owner/task/constraints, and never borrows the
preceding interaction's approval or marks it confirmed. A new approval
requirement prevents this automatic probe; resource quarantine still denies it.
The fixed revision1 credential-free read contract is checked in policy and
runtime. This grants observation only. A separate authenticated owner factual
review may resolve the journal under migration105; its answer creates no grant,
new approval, budget refund or automatic replay. Same-Input continuation requires
canonical known evidence and current execution authority; a DOM or model verdict
is insufficient. Owner-assisted results remain distinct from machine receipts.

Migration102 [isolates stopped attempts](stopped-input-finalization.md) without
reconciling effects or acknowledging them for the owner. Both Core and Broker
deny arbitrary writes across retained session/task uncertainty, including a new
Task. A fresh canonical text reply needs the exact live Input/intent/admission
and complete scoped isolation proof; equivalent unknown replies and untracked
uncertainty deny it. The older owner-acknowledged local-prepare exception remains
separate and is not minted by kernel finalization.

The receiving Core dispatch verifier recognizes the same canonical mode2/3
owner reply rule as Broker. It still requires permanently claimed exact action/
grant/effect identity and then live admission/Input/destination/source guards.
Other prepare controls continue to require their original approval or mandate.


Canonical communication replies to the current owner's operator-pinned
channels are standard capabilities in mode2/3. They require the explicit owning
admission, exact fixed contract, current Input claim, destination hash and source/
export guards; they do not ask permission to answer or ask an owner question.
Mode0 restrictions and mode1 exact approval stay. Delegation, custom recipients,
credentials, changed contracts and explicit denials are not authorized. Ordinary
result publication does not acquire the separate unknown-effect budget exception
for a blocked notice/question. Current grant verification also checks the exact
owning communication Input claim. Saved publication/dispatch/delivery remain distinct.


`web.search` includes its code-owned provider URL in destination caps and
network release even though arguments contain a query. Queries require release
consent unless operator public-web standing consent is enabled. Exact argument
hashes include the query. No custom endpoint/header/credential is accepted.


Operator-only `BUTLER_PUBLIC_WEB_READS_ENABLED=true` grants standing consent to
release public page URLs and search queries through the fixed web readers,
HTTP GET/HEAD and revision3 browser reads/navigation. It defaults false and
cannot be changed through model arguments or stored settings. Prepare,
authorize and pre-dispatch verification all apply the same policy; disabling
it invalidates an unapproved URL release at verification. Explicit mode1 and
contract approval, credentials, custom HTTP headers/bodies, extensions, writes,
owner denials, task authority, destination caps, public DNS/redirect guards and
finite budgets retain their independent checks. An empty registry domain list
still grants no release consent unless this operator option applies. Broad
URL/query release consent includes model-selected queries, so this setting is
an explicit owner choice for autonomous public research.

The migration096 credential vault adds fixed local `credentials.*` controls.
Their canonical schema/hash, owning Input claim, live context and explicit
denials remain mandatory. Asking for a protected owner interaction grants no
credential use. A current owner-approved vault request can authorize only exact
`browser.prepare_fill/prepare_type` local preparation after scope/version checks;
external submission retains ordinary approval/mandate and unknown-effect gates.
The request is not a broad mandate, and a site hint is not a static allowlist.
For the independent-Input loop exception, Action Service derives the protected
request flag from the canonical contract hash, prepare effect, empty credential
refs and current Input claim. Budget admission additionally proves the exact
live intent/Input and acknowledged failed local communication history. This
flag never authorizes secret use, browser preparation or external effects.
Credential controls also lock and verify the exact owning Input claim inside
the PostgreSQL dispatch transaction. They recheck database-clock claim/Input
expiry after budget and admission waits; a replacement claim requires fresh
authorization and a denial spends neither permission nor budget.

A standing owner-goal mandate cannot enumerate future random request IDs.
After Broker pins current credential metadata, finite `creq_<64hex>` field
references may satisfy its credential-locator scope for revision2 local browser
preparation. This grants no secret access by itself: Vault independently checks
the live consent, owner/run/browser/origin/field/account/task versions at release.
Standing tool, resource, effect, time, privacy and explicit-denial boundaries
remain mandatory, including at the PostgreSQL dispatch commit. Static aliases,
token fields and external submission do not receive this exception.

The dormant communication foundation binds exact method/args/contract and a
digest of enabled verified destination snapshots to the current Input claim.
Only message/widget can become ready through explicit kernel composition;
Bootstrap leaves them unavailable. A narrowly bound owner question or blocked
notice may cross the unknown-effect *loop gate*, retaining approval, current
authority, journal, quota and all other budgets. It cannot authorize an external
write or manufacture consent from a preference. See
[scope and evidence](../ai/communication-core-acceptance-20261021.md).

Communication admission/commit verifies the exact private Input claim as well as
the current run/task/lease/fence. An old caller cannot borrow a replacement claim.
The owning publication transaction rechecks goal/mandate authority independently
of an earlier Broker claim and checks dispatch/grant/approval expiry again after
export-policy/storage waits, before committing any staged publication or outbox.

Conversation action slots use the exact live accepted input, owner/session and run when no task is assigned. Task revisions remain required for task slots; cross-run linking is unavailable without a task.

Fixed [tool discovery](tool-discovery.md) controls are credential-free local reads of the current scoped catalog. Only their exact owned contracts/resources qualify as standard operations, including in delegated work. Input/lease/task authority, explicit denials and execution permissions remain independently enforced.

Optional `schedule.*` uses immutable owning contracts and the current private
accepted-input claim, including in taskless conversations. Read/list is DATA;
create/update/cancel is local preparation requiring exact approval or a current
compatible mandate. The owning endpoint reconstructs the actual dispatched
journal/grant/lease and retains finite occurrence/expiry bounds. Service proof,
child output and the saved schedule grant no future effect authority. See
[agent schedules](agent-schedules.md).

Enabled schedule controls are standard for ordinary owner-goal work: omitting
them from the mandate's runtime tool/resource lists does not hide or deny them.
The exact owning contract hash, local resource, no credentials and read/prepare
effect are required. Explicit denies and existing mandate effect, identity,
revision, purpose, hours and expiry checks remain in catalog/authorization/claim.
This is a fixed kernel policy, not a model-authored grant or new future budget.
Unassigned conversation mutations still require exact approval; delegated
permission subsets and scheduled-occurrence mutation fences are unchanged.

Canonical workspace DATA tools require current owning workspace readiness and
the original accepted-input claim pinned privately to the grant. Their immutable
operation/body/path/file snapshot and source context are joined to shared budget
and exact resource admission on the permanent action transaction. A private
one-use ticket reaches only the authenticated workspace runtime; actual physical
confirmation precedes local completion. Source/input/task expiry and stale file
CAS deny admission without partially spending a grant or budget. Lost responses
remain unknown and stop further non-read dispatch in the task tree. No model
argument supplies a filesystem root, credential, authority or evidence verdict.
See [workspace composition](isolated-code-workspaces.md); application rollout
and owner reconciliation remain separate pending gates.

Optional owning `memory.propose_candidate` is a local prepare control. Current
task/private composition readiness and the original accepted-input claim are
required in addition to exact policy authorization, permanent dispatch and shared
budgets. The claim hash stays private in the grant; it never changes the immutable
approved action. Only the owning service publishes a neutral candidate from a
current pinned source. Proposal fields cannot accept a fact or mint owner/scope,
lease/job/input authority, confidence, retry identity or memory head decisions.

Tool Broker authorizes every dispatch, including single calls, batches and
direct Broker RPCs. Missing policy, incompatible contract, expired approval,
failed authority request or missing grant denies execution before a runtime is
called. Models provide proposals and typed credential references; tool args
cannot supply owners, task versions, decisions, worker fences or grants.

## Preparation and dispatch

1. Orchestrator submits the complete action to `PrepareToolCall`.
2. Broker validates the current registry schema and builds a canonical binding.
   Duplicate JSON keys, multiple values and excessive nesting are rejected.
   Object ordering/whitespace are normalized; number precision is retained.
3. Broker reads run/session/task/lease state from orchestrator's authenticated
   private `/internal/action-context` endpoint. Session Service supplies the
   owner and current PostgreSQL lease/fencing epoch. Task Service supplies
   current versions; Run Service retains the pinned admission version.
4. Credential metadata is checked without resolving secrets. The binding pins
   a digest of alias policy, scope, status, reference locator and record version.
5. PostgreSQL stores the exact intent. Required owner approval uses the durable
   approval/continuation service. A bounded mandate is an alternative only where
   autonomy mode, contract and credential policy permit it.
6. `AuthorizeToolCall` verifies the current exact decision or mandate and creates
   a short-lived private grant. `ExecuteToolCall.authorization_id` is system
   metadata outside the model's tool schema.
   Its deadline also cannot outlive the verified exact approval. This bound is
   persisted with the grant and survives a wait between verification and claim;
   approval expiry cannot become a longer dispatch window.
7. Broker revalidates before each secret release, then again directly before
   dispatch. The grant is claimed atomically immediately before runtime entry.

The claim's owning source/lifecycle adapter runs on the same transaction after
the actual grant's matching session/run/lease/fence row is locked `FOR SHARE` and
current run/task/owner policy is checked. Plain Broker RPC context carries no core
worker token. Only this adapter receives a private read-proof token derived from
those checked identities. Caller token and owner Actor metadata are overwritten;
the derivative has nil `ownership.Authority`, cannot acquire a second write fence
and is not returned to the runtime or caller. It does not supply an input claim,
grant sources, renew a lease or authorize a continuation: the owning adapter still
checks its durable input and every current source/055 identity. A denied adapter
rolls back the existing grant/effect/budget transaction. Replay and fresh-clock
expiry checks remain mandatory.

The binding includes action/run/tool-call identity, canonical argument hash,
relevant full registry contract hash, concrete resource, credential alias/field
references and metadata digest, task/constraints versions, owner and effect
class. Any change invalidates earlier approval. The same run/tool-call identity
cannot be reused for different args. A resumed worker retains the approved
intent and acquires a fresh grant under its new lease/fence. An unused grant
may be refreshed; a dispatched grant cannot be refreshed.

Prepare/authorize/execute RPCs require a private service token. Knowing `run_id`
cannot impersonate a worker. Read-only catalog inspection remains available.
Both gRPC and private HTTP tokens come from a mounted secret file. HTTP
authority calls use a direct transport without ambient provider proxies, reject
redirects, bound response size and time out after three seconds. Private
delegation admission uses the same direct-connection rule. Failures deny actions.
The baseline uses the trusted Compose backend
network; externally exposed deployments must use encrypted transport.

## Effects and autonomy

Effect classes are `read`, `prepare`, `commit`, `unknown`. Fixed read tools and
conventional HTTP GET/HEAD/OPTIONS are read effects; HTTP mutations are commits.
Credential storage installation is preparation. Browser interactions and
Chromium navigation, including independent `browser.read`, are unknown because
website JavaScript can submit, purchase or autosave. Model descriptions cannot
downgrade an effect.

`BUTLER_AUTONOMY_MODE` is explicit, defaulting to `mode_1`:

- Mode 0 permits verified reads without credentials.
- Mode 1 requires exact owner confirmation before every dispatch.
- Modes 2/3 may execute compatible reads; other effects require exact approval
  or an active bounded mandate covering the actual effect.

Contract-required approval, including `single_tab.bind`, remains mandatory;
mandates cannot bypass it. `always_confirm` credentials require exact approval.
`auto_read_only` forbids mutation even with approval; `manual_only` cannot be
used by the agent. An approval authorizes the exact alias/field/resource/action
combination and never changes the alias's global policy.

## Bounded mandates

For owner-goal `browser.snapshot/freeze_snapshot/extract_text/close`, public
arguments identify a context rather than a URL. Broker resolves its current
observed URL and control epoch from the live broker-owned session row, matching
the exact run/owner/Task. This metadata is included in the action hash; it never
comes from model args. URL allow/deny scopes and the explicit tool/read effect
still apply. Foreign, expired, closed and changed-epoch contexts fail closed.
Before page bytes are released, the actual result URL is checked against current
Task/goal/mandate and goal-wide denials, with the current browser epoch retained.
An out-of-scope result is scrubbed and the spent read remains conservatively
uncertain. Close returns no page bytes. No navigation/input/credential action
can use this resource projection, and click approval remains independent.

An owner-goal mandate covering `unknown` browser.click can authorize it without
an individual approval when the loaded contract does not require approval.
Task prose is not an additional machine-enforced confirmation flag. A mandate
limited to read/prepare instead denies click entirely, including preparation of
an approval for an out-of-scope effect. To permit scoped submission while still
requiring an exact decision, the authoritative operator registry must set
click `requires_approval=true`; this contract rule has priority over mandates.
Its changed full contract hash fences old intents/grants. This is an existing
configuration mechanism, not a new permission or a default registry change.
The isolated owner-mandate Chromium acceptance qualifies this stricter variant
only; deployment and native/delivery qualification remain separate.

Mandates bind an owner/task/task version/constraints version to exact tool
names, exact HTTP(S) origins or non-URL tool resources, explicit effect classes
and credential alias/field references. Wildcards are rejected. Expiry is at
most seven days. Scope changes require the next revision; revoked mandates
cannot be reopened. Grants recheck current revision/revocation; dispatch CAS
checks the mandate again. Child execution receives no independent permission.

The operator endpoint `/internal/action-mandates` on Broker accepts POST to
create/update and DELETE to revoke. It requires the private service token and
authoritative active owner/task versions from the supplied run. Request owner
fields are compared to current state, never trusted as identity. The payload
contains `run_id`, `owner_id` and typed `mandate`. Assign its ID with
`BUTLER_ACTION_MANDATE_ID`. This endpoint is not a model tool or unauthenticated
public API. Amendments, cancellation, owner changes, expiry and takeover
invalidate incompatible permissions before the next secret/effect boundary.

## Secrets and uncertain outcomes

Broad `owner_goal` mandates are a separate authenticated owner-service contract,
specified in [owner goals](owner-goals-mandates-spec.md). They do not use Broker's
legacy task-mandate writer. Trusted task assignments pin goal, mandate and
purpose-policy versions; canonical bindings retain those versions and exact
purpose. Scope/status/hours and deny checks occur before credential inspection;
actual dispatch rechecks current authority in its ownership/run/task transaction
before atomic budget reservation and grant spend. Models cannot choose an
arbitrary broad mandate through args. Original finite limits/deadline survive
edits and fresh runs. An expired, paused or revoked assignment denies exact
approval reuse as well as autonomous execution.

Secrets remain outside bindings/grants/notifications/model args. Only metadata
digests and references cross these boundaries. Credential Broker checks
metadata again before resolution. Browser runtime checks actual current URL,
fixed origin, observation version and owner before injection. Broker masks
known resolved values in runtime results/errors, including JSON strings,
common URL encodings and base64. Browser contexts never export raw
cookies/storage/passwords.

Locator/alias metadata changes invalidate approval. Rotating a value behind an
unchanged `env://` locator must also update the credential record's version
(`updated_at`); preparation does not read secret material to fingerprint it.

Grant states are `authorized`, `inflight`, `dispatch_completed`, `unknown`,
`revoked`. Claim happens after final checks, not at preparation/secret resolution.
`dispatch_completed` means a completed runtime response; it does not prove a
verified external effect. Timeout, runtime failure, missing result or outcome
write failure leaves a non-reusable grant and returns `effect_unknown`.
Orchestrator records this result then stops before model continuation with
`ErrActionOutcomeUnknown`. Owner verification is required before a new attempt.
An owner can abandon a stopped taskless communication Input through its typed
failure control while explicitly acknowledging the exact retained UNKNOWN local
publication IDs. This changes only Input/run failure and its audit: the effect,
grant, evidence, reservations and delivery remain unchanged. It neither verifies
the effect nor permits its retry. Executing and non-communication uncertain writes
are ineligible. Ordinary unknown-effect guards and Broker mediation remain intact.
For a different taskless owner Input only, a fixed `communication.message`
publication may cross the loop gate when every conflicting uncertainty is an
acknowledged local message/widget prepare from a failed old Input/run with a
closed-with-failure obligation and all three failure/uncertainty audit events.
The old declared revision1 contract must specify `local_runtime_ack`; this
qualifies locality, never an assertion that an acknowledgement was observed.
Current intent/args/contract, owner/session/original event, live claim, destination
digest and admission method/quota are rechecked. The old journal/grant remains
unknown and non-reusable. Executing work, external effects, same original Input,
missing provenance/audit, Task work and other tools retain the normal stop.
Current approval, source checks, Broker and finite budgets are still mandatory;
this does not authorize another attempt at the abandoned effect.
Dispatch/result checkpoints preserve this boundary during recovery. Migration
035 adds the [external effect journal](external-effect-journal.md), permanent
trusted intent slots, declared recipient protocols and independent evidence.
Technical completion without supported evidence remains unknown. This contract
does not claim exactly-once effects for arbitrary remote services.

Revocation cannot undo effects already sent to an external service. Browser
sessions remain transient/run-local across process loss; approval cannot
resurrect a lost browser context.

## Operations and validation

Stopped historical local actions have a kernel-only bounded review for the two
explicit compatibility pins in [stopped finalization](stopped-input-finalization.md).
It uses original canonical bindings and terminal executor locks. Immutable
publication receipt or fenced transaction absence can resolve the local effect;
read no-write proof leaves the read UNKNOWN. This is not a grant, refund,
arbitrary external reconciliation API or proof of channel delivery.

Migration `031_action_authorization` creates intent/grant/mandate tables. Durable
approval bindings use the approval service/migration. Compose mounts a private
authority token into orchestrator and Broker. Generate
`.secrets/action-authority.token` (at least 32 random characters, private file
permissions) or configure another secret source. The lab helper generates it
outside snapshots under the lab's secrets directory. Missing auth wiring fails
closed, without a legacy bypass.

Lab tests cover hashes, changed resources/accounts/tools/versions, expiry,
revocation, outage, lease takeover, credential metadata changes, preparation
versus submit, reflected secrets and uncertain outcomes. Isolated PostgreSQL
tests use `butler_actionauth_test` with disposable schemas: 24 concurrent claims
produce one winner. Real e2e runs actual Broker/browser processes and real
PostgreSQL owner approval through the authenticated private reader. It injects
an approved password in Chromium, submits a multi-field form once, rejects
changed args/replay and verifies absence of secrets from approval state.
The boundary fixture uses inert checkpoint hooks; full ingress/restart recovery
belongs to the durable lifecycle suite.

`scripts/dev/lab-browser.sh` runs browser/runtime/Broker/approval e2e in existing
Playwright and disposable Go containers under an isolated agent root. It does
not change running Compose services or production database tables.
