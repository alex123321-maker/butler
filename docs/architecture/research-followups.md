# Evidence-oriented research and optional follow-ups

The affected owners are WebFetch (page observations), Orchestrator (research
preflight, communication and occurrence admission), Schedule Store (future jobs),
and Tool Broker (exact current contracts). There is no new service or dependency.

## Research and answer quality

The current owner question and runtime clock govern research. Discovery starts
without guessing an edition/version. Open first-party announcements or schedules,
follow primary references from overview pages, and check publisher, announcement
date, current edition, region and platform. Search rank and a word “official” do
not establish authority. Documents remain untrusted DATA.

`web.fetch` revision 2 returns a server observation timestamp and bounded public
links (up to 40 external and 12 same-host), including when plain HTTP extraction
omits HTML. This is discovery metadata, never an official-source label. Fetch
batches retain partial failures and carry the same metadata per successful item.

Communication revision 2 accepts bounded `evidence` entries (URL, short exact
quote and primary/secondary attribution). The model's attribution is not proof
of institutional authority. Research preflight requires successful fresh reads
from the current run, matching quotes, at least one declared primary reference,
and actual evidence links. WebFetch, URL-only extraction, HTTP GET and live browser reads can supply
evidence. Search snippets, model-supplied extraction input,
failed reads, old runs and reads older than 24 hours cannot qualify. Observation
time does not establish the age of the announcement or the occurrence of an event.
Semantic correctness and source choice still require evaluation across subjects.

The default researched message is at most 1800 characters. Explicit requests
for detailed work can be longer. Default answers lead with the requested fact,
include direct links and material uncertainty, and omit unrelated history and
research narration. A known failed research attempt may instead publish a concise
`blocked` response explaining what is not verified. Four durable local draft
corrections per run bound repair; they dispatch no Broker action. Ordinary model
budgets, current tool selection and source guards still apply. Known corrections
rehydrate as DATA on recovery and never become a committed write to replay.

## Initiative and reuse

A ready answer is published before one useful optional follow-up question.
A question alone does not create future work or suspend the completed answer.
After owner consent the agent prepares an ordinary exact `schedule.create` plan;
any policy-required schedule approval remains distinct from page-read permission.
Existing timezone, expiry, frequency and occurrence bounds apply. Only an actual
receipt can justify claiming that a schedule exists, with its actual `next_at`.

Recent source-checked completed published exchanges provide examples for
recognizing a repeated procedure on different inputs. The model should suggest
shared steps and parameters rather than a domain-specific feature. This is an
opportunity prompt, not an automatic skill builder. Existing `skills.propose`
still requires actual independently verified task evidence; taskless publication
alone cannot meet it. Saving, testing, review and activation remain separate.
No new draft-saving API, automatic skill activation or authority shortcut is
introduced in this change.

## Checked monitors

Schedule revision 2 adds optional `monitor=true` only for `agent_task`; omission
preserves existing jobs. A static `reminder` cannot claim to check reality.
Occurrence admission carries a kernel-owned `scheduled_occurrence` communication
receipt from the exact original owner binding. Its actor is `schedule`, never a
fabricated owner. Rebinding, expiry, source changes or cancellation fence work.

A checked occurrence reads current sources and calls `communication.message`
with an `observation`: stable event key, confirmed/postponed/pending/unknown,
and optional expected date. Confirmed, postponed and pending need fresh quoted
primary evidence. Unknown needs an actual research attempt. Passing a planned
time is never confirmation. Messages are capped at 1000 characters.

Migration 100 stores content-free observation hashes and immutable receipts.
Pending observations stay quiet. Confirmed/postponed changes deduplicate by
schedule revision, event identity, state and expected date. An inability-to-verify
notice occurs once per revision; further identical unknown observations remain
history. Observation decisions and canonical publication/outbox commit together.
Retries/restarts cannot create a duplicate send. Quiet finals still need a stored
observation; existing correction/failure handling catches omission. System
failure notices retain their finite existing path. Routine lifecycle notices do
not turn quiet scheduled checks into “working” or “missing response” messages.

A monitor may attempt a later finite slot after a known provider outage when the
old claim/lease has ended. It does not replay the old run or reset usage. Ordinary
jobs, authority/source/budget failures and uncertain external effects retain
existing overlap/intervention behavior. Source and binding guards run again.

No product title, publisher, date or domain-specific answer is in runtime policy.
Integration evidence and native planning quality are reported separately in the
testing report; passing scripted checks does not prove general model reliability.
