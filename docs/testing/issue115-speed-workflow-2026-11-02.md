# Prospective latency workflow

This new window preserves all closed plans, traces, failures and expenses. The
same byte-pinned 12-case workflow and Latin A/B/C order run under five explicit
profiles: Gemini MEDIUM (existing Flash High Cloud Code route), Gemini LOW
(existing Flash Low route), and OpenAI Luna max/high/low. The route label is not
an observed thinking level; native wire settings and observed model versions
are recorded separately. Google documents LOW/MEDIUM/HIGH for Gemini 3.8 Flash:
https://ai.google.dev/gemini-api/docs/thinking. Luna supports the selected efforts:
https://developers.openai.com/api/docs/models/gpt-6-luna.

Every new profile declares 65536 input/32768 output, 90s per method, 13 methods
per task and existing 420s authority/480s case bounds. No in-window limit
escalation, retry, fallback or old-root resume. Total denominator is 180 tasks.
The output ceiling includes reasoning; max effort does not mean unlimited
generation. Increasing output can increase expense and duration.

The new `latency-v1` composition enables:

- An exact task-bound collector selection of the reviewed migration skill for
  the eight applicable C tasks. Core executes actual skills.load through its
  ordinary action authorization, Broker, budgets, source checks and durable
  ref-only transcript before first inference. It does not inject a fake model
  call or a synthetic successful load. Unrelated controls select no initial
  skill. This deterministic fixture binding is not general natural-language
  applicability or autonomous selection. Product startup supplies no resolver.
- Omission of the redundant flat tool summary only with complete native tool
  definitions and no deferred discovery. Whole current source observations,
  owner constraints, history, schema bounds and source identities are retained.
  Repeated skill context assembly refreshes descriptions/pins instead of
  accumulating duplicates. No lossy summarizer is introduced.
- Provisional plain-text forwarding during native capture. Other events,
  including mixed delta/action payloads, tool proposals, finals and usage, wait
  for complete PostgreSQL and raw/fsync receipts. Errors retain costs and grant
  no retry. Existing source/skill/authority guards remain outside capture.

Measure full task duration, weighted mean provider boundary latency, system
elapsed excluding provider wait, actual tool RPC subset, preparation/observer,
tokens, known-usage tariff bounds and nullable first text at Core's delivery
sink. Provider wait includes network/adapter and is not pure thinking. Concurrent
delta validation/delivery overlaps provider wait; elapsed subtraction is not a
CPU breakdown. A local sink measurement is not Telegram/Web rendering latency.

The control gate must pass the existing 72 tasks, original 36 workflow tasks
and new 36 optimized workflow tasks, actual Broker review/approval/restart,
race/vet and streaming boundary tests without required skips or native calls.
Every new native root pins previous receipts, committed source, plan, binary,
kernel isolation and unique journal namespace before authentication/dispatch.
The unchanged evaluator reports strict final/evidence success and physical
checked artifact correctness separately. No expected answer is passed to the
provider. Failed and unexecuted tasks stay in the denominator, unknown spend
stays unknown. This open development corpus does not prove quality equivalence.

Both optimizations and output bounds differ from the old baseline. Old/new
differences therefore do not isolate effort or output cap causally; the new
profiles share the same optimizations and bounds. Scripts use Python only for
stdlib artifact analysis and private host SSH launch, never product execution.
