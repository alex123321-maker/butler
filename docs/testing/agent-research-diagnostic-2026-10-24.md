# Диагностика обычного исследовательского запроса — 24 октября 2026

## Область проверки

Запрос владельца: «Попробуй найти время и даты выхода нового сезона монолога
фармацевта». Цель проверки — качество общего пользовательского пути Butler,
а не специальная реализация поиска расписания одного аниме.

Проверены исходные PostgreSQL-записи Input/Run/transcript/tool calls,
model accounting, prepared context, approvals/publications/outbox и текущая
композиция `butler-main` на `laba`. Прямых записей в продуктовые таблицы нет:
повтор, согласование и закрытие неудачной попытки идут через owning owner API.
Значения секретов в отчёт не включены. Python использовался только как
операторский HTTP/JSON-клиент стандартной библиотеки на сервере; core/runtime
остаются на Go.

Исходный запуск был из Telegram. Повтор использует обычный Web ingress того же
развёрнутого приложения, модели, Broker и owner policy, чтобы не смешивать
его с чужой проверкой в Telegram. Это не точная копия истории Telegram и не
проверка отображения в Telegram-клиенте. Browser Codex не подключился из-за
отсутствующего runtime-модуля; переписка и выполнение исследованы через
владеющие сервисы и PostgreSQL, не через обход Telegram-аутентификации.

## Как должен выглядеть успешный путь

1. Понять название и проверить, какой сезон актуален на сегодняшнюю дату.
   Небольшая неточность названия не должна требовать уточнения, если объект ясен.
2. Найти актуальные источники обычным поисковым инструментом и открыть
   официальный анонс/расписание. Выбирать сезон по источникам, а не по памяти модели.
3. Проверить дату публикации, исключения в расписании, различие ТВ-премьеры,
   стриминга и локальной озвучки. Не придумывать время ещё не объявленной озвучки.
4. Показать ближайшие даты и время с явной зоной; при наличии подтверждённого
   часового пояса владельца добавить его. Сохранить ссылки и дату проверки.
5. Доставить компактный результат. При невозможности — конкретное объяснение
   и частичный подтверждённый результат. Ожидание решения/ошибка должны быть
   видимыми независимо от способности модели вызвать communication-инструмент.

Проверяемый ориентир существует: официальный анонс третьего сезона опубликован
15 августа 2026, премьера — 2 октября в 23:00 JST. В официальном октябрьском
календаре серия 30 октября отдельно указана на 23:40 JST. Поэтому ответ
«второй сезон, январь 2025» и механическое «каждую пятницу в 23:00» недостаточны.
Это независимая проверка исследователя, а не сведения, добытые Butler:

- [Официальный анонс](https://kusuriyanohitorigoto.jp/news/2623/).
- [Официальный календарь](https://kusuriyanohitorigoto.jp/).
- [Публикация октябрьского календаря](https://kusuriyanohitorigoto.jp/news/2971/).

Например, 23:00 JST соответствует 21:00 Asia/Tomsk, а 23:40 JST — 21:40.
Исключение показывает, почему пересказ обычного недельного слота недостаточен.

поиском в интернете, а `credentials.search` не отвечает цели исследования.

Создан pending approval `approval-1792851896824575749-4e5701e41662`.
Причина — отдельный URL/query release gate: пустой `allowed_domains` разрешает
маршрутизацию к публичным адресам, но сам по себе не является согласием на
отправку модельного URL/query. Называть причиной только `mode_2` неточно:
эта автономность допускает совместимые reads; сработал независимый release gate.

`channel_delivery_events` есть `status=sent`, tool events `sent` и
`approval_request=waiting_reply`. Фактически startup explicit composition
подключает logging delivery sink до создания explicit Telegram adapter;
он не добавляется к этому sink. Нулевая ошибка логирования не подтверждает
доставку пользователю. `suspendApproval` сохраняет решение, но игнорирует ошибку
доставки; отдельного durable approval outbox в этом пути нет.

## Контекст и смешение целей

В исходном prepared context 46 InputItems. Кроме текущего запроса туда вошли
многочисленные проверки виджетов/оформления и ответы про сервировку и упаковку.
Working Memory: idle, пустая цель. В MemoryBundle — четыре нерелевантных
уведомления о встрече и финансовых событиях. Значения/имена/суммы здесь намеренно
не копируются. Те же четыре нерелевантных chunk выбраны и в Web-повторе.

Более сильное свидетельство: run `run-1792815486188302094-1b0c052b0f42c676`
начался с вопроса о скатерти и получил ответ владельца про скатерть. Однако
его publication и final дополнительно утверждают расписание второго сезона
за 2025 год. В run были только discovery/load/communication, без внешних чтений.
Final сохранён как `unverified`. Это реальное смешение целей и неподтверждённый
ответ на старый вопрос, а не гипотеза о вреде большого контекста.

В system items исходного и повторного prepared context нет явного текущего
времени/даты и зоны владельца. Даты внутри случайных воспоминаний не заменяют
авторитетную временную привязку. Нужен проверяемый текущий temporal context,
особенно для слов «новый», «сейчас», «ближайший».

## Изменение по явному указанию владельца

После показа согласования владелец потребовал убрать такие разрешения и
разрешить агенту самостоятельно ходить по страницам.

Коммит `f9d51f57` добавляет operator-only
`BUTLER_PUBLIC_WEB_READS_ENABLED` (по умолчанию false) в Broker:

- фиксированные web readers, HTTP GET/HEAD и browser navigation revision3
  могут отправлять публичные URL/query без отдельного release approval;
- prepare, authorize и verify используют одну политику;
- выключение настройки запрещает verification unapproved URL release;
- режим подтверждения каждого действия, contract-required approvals,
  credentials/custom headers/body, writes/extensions, source/task authority,
  destination caps, DNS/redirect guards и бюджеты проверяются независимо;
- настройка отсутствует в managed settings и модельных аргументах.

Это реализация согласия владельца на самостоятельный public research,
а не wildcard в credential policy и не отключение Tool Broker.

## Повтор с самостоятельным чтением: найден crash WebFetch

Run: `run-1792852785690199076-5d64f33e1bff00fa`.
Агент сделал четыре search каталога, один load и выбрал
`web.fetch(https://en.wikipedia.org/wiki/The_Apothecary_Diaries)`.
Все шесть intents имеют `requires_approval=false`. Это реальная проверка новой
политики через обычные Core/Broker/grant/dispatch, не только unit test.

На внешнем чтении процесс `tool-webfetch` упал. Stack trace содержит
`(*SelfHostedProvider).Fetch(0x0, ...)` в `server.go:275`.
Пустая настройка primary возвращает `*SelfHostedProvider(nil)`, но после
преобразования к интерфейсу `Provider` сравнение `provider != nil` истинно.
Такой элемент попадал в цепочку и падал до Jina/plain HTTP fallback.
Этот дефект существует независимо от провайдера модели и поисковой темы.

Broker правильно сохранил отсутствие подтверждённого ответа как
`effect_unknown`, но пользовательское исследование целиком остановилось на
ошибке чтения. Нет ни объяснения от агента, ни попытки прочитать другой источник.
Для будущего улучшения нужен отдельный проверяемый путь обработки неудачных
read-only операций; ослабление правил неизвестных writes не требуется.

Коммит `873105a1` исключает typed nil providers из цепочки. Два новых regression
tests воспроизводят обычный startup с пустыми optional URL: реально читают
контролируемую HTTP-страницу через plain fallback и проверяют bounded failure
пустой цепочки. Windows и Linux/race `go test ./apps/tool-webfetch/...`, а также
Linux `go vet ./apps/tool-webfetch/...` прошли.

Реальные результаты обычного агентного пути:

2. `web.fetch` Wikipedia завершился без panic через `plain_http_fallback`,

   Статус tool=completed здесь означает доставленное наблюдение, а не
   успешное извлечение искомых сведений.
3. Агент загрузил `browser.read` и открыл ту же страницу через браузер.
   Получен реальный текст страницы, `status=completed`, `ok=true`.
4. Следующее продолжение остановлено с
   `budget_provider_input_bytes_conversation`. Approvals=0, publications=0.

Итого: девять наблюдаемых model requests, 58 603 входных токена, 368 выходных
токенов; интервал model observations 14:44:54–14:45:35 UTC. Исследование ещё не
завершено: проверенного расписания и результата для пользователя нет.

Это квалифицирует самостоятельный public fetch/browser путь и отсутствие
конкретного crash, но не качество решения. Остановка относится к общему
накопленному бюджету Web conversation, в котором уже шли другие проверки и
повторы этого эксперимента. Её нельзя выдавать за размер/стоимость одного
чистого нового поручения. Лимиты и историю reservations не сбрасывали.
Последний диагностический Input также закрыт штатным close-failed API;
работающих/ожидающих тестовых вводов после проверки не оставлено.

Дополнительные общие проблемы: HTTP fallback не задаёт вежливый явный
User-Agent, а потребитель должен отличать HTTP403 от данных страницы. Даже
после успешной смены инструмента остановка бюджета не даёт пользователю
объяснения или уже полученного частичного результата. Следующий опыт стоит
проводить на свежей поддерживаемой conversation/task, явно отделяя её лимиты
от исторического общего чата, а не увеличивать старые durable scopes задним числом.

Фактический daily conversation scope для `primary-web-v1:2026-10-24`:
лимит 402 653 184 байта (384 MiB), учтено 394 266 709 байт к остановке.
Остатка не хватило для следующего консервативного reservation. Это не
«википедийная страница заняла 384 MiB»: учитываются все прошлые запросы дня
и зарезервированные полные provider inputs; нативный usage и reservation
измеряют разные величины.

## Приоритет общих улучшений

| Приоритет | Изменение | Критерий приёмки |
|---|---|---|
| P1 | Доставляемые состояния waiting/error/blocked, независимые от модели | Сохранённый запрос решения получает реальное канальное представление/receipt; logging не считается sent |
| P1 | Надёжное завершение model turn и восстановление после временного сбоя | Остановка укладывается в deadline; причина понятна, безопасное продолжение не повторяет неизвестный эффект |
| P1 | Обработка неудачного чтения и рабочие fallback providers | Пустой primary не роняет runtime; неудача одного read позволяет осмысленно выбрать доступный источник с сохранением бюджета и журнала |
| P1 | Настоящий web search через Broker | Один query возвращает URL/title/snippet/date; затем читаются первоисточники; пустой поиск не превращается в выдуманный ответ |
| P1 | Фокус текущей цели и право не извлекать нерелевантную память | Вопрос про сериал не тянет финансовые уведомления; следующий вопрос про скатерть не отвечает про сериал |
| P1 | Проверка актуальности и доказательств | Текущая дата известна; «новый сезон» определяется по источникам; unsupported claims остаются неопределёнными |
| P2 | Удобство discovery | Минимум служебных turns; однозначные capability descriptions и доступные рецепты поиска, без хрупкого ручного обхода каталога |
| P2 | Независимость новых разговорных целей | Остановленное поручение не делает весь чат недоступным; порядок и unknown-effect ограничения сохраняются внутри соответствующей работы |

Снятие поштучных URL approvals исправляет один барьер. Оно само по себе не
доказывает качество исследования, корректность ответа или доставку результата.
Эти критерии следует проверять на фиксированном наборе обычных поручений
с измерением успеха, актуальности, времени, служебных/model turns и реальных
канальных receipts. Успех вызова инструмента или `run=completed` недостаточен.
