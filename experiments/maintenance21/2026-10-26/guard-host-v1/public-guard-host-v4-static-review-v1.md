## Finding: initial prepare must distinguish never-started from cleanup ownership

At capsule_guard_host_linux.go:136, initial preparation calls `inspect(ctx,false)`. Its test at:165 only distinguishes running versus not-running; `capsuleOwnedState` at:233 accepts both `created` and `exited`. Thus an unexpected start/exit between this host's create and cold inspection is not rejected as a lifecycle change: preparation can call start again. The final witness at:525 hardcodes `CandidateExecuted:false`, although current guard/exe/absent-marker measurements do not establish that this owned object was never previously run.

This is a concrete static gap under unexpected prior lifecycle/interleaving, not a claim that v4's actual process had run the candidate. Candidate code cannot normally initiate this race because it has not run or acquired the private Docker handle. Keep `created|exited` in the narrow owned-cleanup helper, but initial preparation should separately require exact `created`, no running PID, never-started timestamps/restart state, and reject any already-used lifecycle before issuing a fresh guard-only witness. Recheck expected first start/current PID identity before qualification. No new independent experiment was run to assert the original failure occurred.

## Limits and next implementation risks

1. `measure` writes group/control/stage without the mutex used by `close`. Current prepare invokes it synchronously before returning a usable handle. Before adding marker publication/run I/O, define one serialized lifecycle owner (or one shared mutex/state machine) for remeasurement, publication, run and close. Never reuse the cached witness as fresh admission, overwrite/leak an old control handle or publish through a concurrently closed/stale tmpfs descriptor. Bind the actual control inode/mount and PID/start/runtime again at publication.
2. Physical namespace/mount/descriptor witness hashes are useful pins but not their raw preimages. This checker reviewed the actual predicate/source and saved process record, not a new direct kernel inspection. `Seccomp:2` establishes filtering mode, not a separately measured filter policy. The mount predicate is a fixed point/flag allowlist, not an independent forensic attestation of every default Docker backing source. Private daemon/topology remain trusted host configuration; do not claim protection against an already privileged malicious daemon/host.
3. Close is mutex-protected, one-shot and caches its result. Successful cleanup requires kill/wait, stopped exact owned identity/PID0, zero-or-removed cgroup tasks and DELETE; a repeated successful Close issues no extra API. Any failed close remains failed and does not promise absence of residual processes. It returns early on control-handle close failure or any Docker error; before candidate execution exists, ensure all callers treat that as unqualified containment and do not proceed to another launch. An implementation may retain the error while best-effort stopping exact owned objects, but it must not hide it or automatically retry an uncertain maintenance effect.
4. A failed create with unknown ID retains only the random owned name. It must remain an explicit possible cold object for operator investigation, not zero residual state. Earlier v1 cleanup failure and its separate exact cold deletion remain original failures; later v4 success does not repair their history.
