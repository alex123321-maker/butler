# Issue21 fixed capsule functional runner/checker — PREPARED_ONLY

This is a proposed minimal public acceptance contract, not a formal freeze, permission, successful check or release approval. No hidden cases or private expected answers have been authored for it. It applies only to a separately pinned, dependency-free, ordinary capsule target on this PC and synthetic data. It does not establish permission or compatibility for updating a monolithic/protected Core. The actual issue21 and maintenance architecture remain the acceptance requirements.

## Trusted inputs and independent owners

The operator selects one exact target/profile, source origin/commit boundary, baseline and candidate source inventories, fixed compiler image/module, guard executable, deployment topology, capsule request/response schema, state/protocol compatibility rule, checker binary, fixed/hidden corpus commitments and criteria. The author's request supplies an immutable candidate version only; it cannot select commands, Dockerfiles, tests, checker, keys, socket, mounts, target, URLs, thresholds or protection class. The complete inventory includes submitted tests/configuration even though those files do not choose the build or test procedure.

Use separate real processes for (a) trusted checker, (b) independent owner/controller, and (c) narrowly configured node executor/inspector. The candidate/author receives none of their signing seeds, owner/node bearer credentials, PG credentials, live memory, host paths, Docker sockets or expected outputs. Checker, controller and node keys are distinct under the existing Profile contract. A checker private key may sign only that process's own completed evidence; no author-accessible arbitrary `SignReview` endpoint or caller-provided pass report is allowed. The node signs its measured physical outcome, not a request-supplied artifact identity. Opaque report/receipt references may leave these processes; secret values may not.

The first fixed capsule protocol should be a small bounded pure transformation with an externally observable result, for example render/validate synthetic report data. Before freeze the operator must specify its exact JSON schema, error codes, input/output byte limits, serialization and expected functional rule; this document deliberately contains no hidden business values. Use one fixed operation or a fixed whitelist, no shell/path/URL/plugin selection. Individual case input may reach the capsule; hidden corpus files, goldens, checker source and signature key must not be mounted there. Candidate stdout is untrusted DATA, never an authoritative test verdict or deployment command.

The initial pure capsule may have no direct persistent state or database access. That does not waive compatibility: the real pending task/approval/checkpoint lives in owning Butler services and must survive a capsule update. Conversely, success on this stateless target is not evidence that arbitrary Core schemas or all service continuations are compatible.

## Public check families before any hidden authorship

Freeze exact fixed cases and separate independently authored hidden controls covering: working repair of the original task; compile/launch failure; alive but wrong functional result; malformed/oversized output; incompatible active protocol/schema; submitted-test manipulation; attempted protected-policy/updater changes under ordinary permission; changed current base; owner stop before/during admitted change; lost outcome without replay; compatible active approval continuation; explicit incompatible continuation denial; return to retained working version. Existing component tests remain supplementary and failures remain immutable.

No new fault-injection code is authorized by this proposed contract. Use existing public cases where they suffice; any necessary new implementation/testing is a separate coordinated task. An independently authored hidden set begins only after the public target/interface/checker/source/criteria are frozen and preserved, then hashes bind literally. Author, checker and report signer roles and process boundary are recorded prospectively.

## Evidence envelope and verdict

A run manifest must pin source commits and complete inventories, compiler/module/package/guard/candidate/image/runtime identities, operator profile revision, supported target class, checker/fixed/hidden corpus/criteria, synthetic provenance, exact finite time/memory/CPU/PID/swap/bytes/operations/native bounds, plan/case identities and stop rules. Use the existing numeric maxima or stricter fixed bounds; do not raise a failed check's limit. Freeze concrete values before execution, not author-controlled defaults.

For each planned case retain baseline/candidate observed functional verdict, real evidence refs/hashes, process exit/join, actual task/Input/run/approval/intent/effect IDs and revisions where applicable, schema/protocol/currentness, owner stop epoch, claim/attempt/fence, dispatch count, measured physical old/new artifact/runtime, and deployment/trial/rollback outcomes. Distinguish build, exec, live, ready, function, task, effect, delivery, review and deployment status. A case not run is unavailable, not PASS. Keep planned denominators and original first stop; no replacement cases or retrospective threshold changes.

The signer reads immutable verifier-owned evidence, not an author verdict. Verify its signature against the operator-pinned public key through the existing Store. Record native admissions as measured zero for a deterministic offline runner; if a later permitted check uses native models, include all failed/unknown expense and keep unknown spend nonzero/unknown. Quality/error/cost benefit pertains to the measured original task, never the number of changes or green health checks.

Publish only an explicit safe evidence allowlist; keep private keys/auth/settings, live data, private goldens and hidden-case helper source out. A public capsule pilot can qualify only its declared ordinary target. Full issue21 closure additionally requires all literal criteria, including protected-change permission separation and the real preservation/rollback scenarios, not this PREPARED_ONLY contract or present component logs.
