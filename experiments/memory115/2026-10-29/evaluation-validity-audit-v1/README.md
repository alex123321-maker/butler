# Аудит пригодности A/B/C для оценки пользы памяти

Проверено 29 октября 2026 на laba, без новых обращений к модели. Источник —
неизменённые raw/DB-выгрузки полного v6 и код производителя
`9eea1672e7303c6d87ee9cc210e1a681e29f183e`. Исторический отчёт и оценки
[v6](../guided-full-v6/README.md) сохранены. Это аудит постановки и ограничений
оценщика автором исследования, а не независимая квалификация #115.

**Вывод:** эксперимент обнаружил реальные интеграционные ошибки и расходы,
но его задач недостаточно для вывода «агенту не нужна память». Повторять этот
же набор ради доказательства пользы памяти сейчас нецелесообразно. При этом
наблюдаемая дороговизна выбранного режима памяти реальна и требует объяснения.

## Что удалось подтвердить

- Все 48 контролей представлены. В каждой из 16 троек case/repetition первые
  фактические инспекции показывают одинаковые файл, ревизию, окружение,
  допустимое значение и статус проверки во всех трёх вариантах.
- Collector замораживает подготовку до контролей; каждый контроль клонирует
  одну замороженную БД. Seed текущего файла зависит от case/repetition, но не
  от arm. Отзыв источника применяется отдельно в каждом соответствующем клоне.
  Контрольные результаты не возвращаются в обучающий набор.
- В C действительно были четыре загрузки навыка через Broker с актуальными
  pins, до первого действия по проекту. Это не имитация загрузки.
- Прежние учёт расходов, неизвестный usage и неуспешные попытки сохранены.
  SHA256 raw-архива повторно совпал:
  `5a4ca8064fdab2ca3b17f1ca147a5a7a046d1afdf2a8b5031701e0ea8375e156`.

Основания: `memory_experience_native_collect_test.go` (freeze, control, recipient),
`memory_experience_native_clone_test.go` (clone), фактические инспекции в
[facts.json](facts.json), прежние Broker/cost proofs v6. Это ограниченная проверка
изоляции; равенство первых инспекций не доказывает равенство всех скрытых факторов.

## Почему тест слабо измеряет пользу памяти

### 1. Положительные задачи практически решаются заново одним чтением

`extension.project.inspect` возвращает `accepted_ready_value`, полный текущий
README и его revision. Это обнаружено во всех **53 фактических инспекциях**.
Подготовка сводится к замене флага и проверке нового неприменённого артефакта.
Память не устраняет обязательную проверку текущей ревизии и результата.

В [recipient](../../../../apps/orchestrator/internal/app/memory_experience_recipient_test.go)
это видно в обработчике GET `/project/<resource>` и `validProposal`.
Интерфейс сообщает законные текущие данные: это не утечка скрытого ответа
оценщика. Скрывать полезные текущие данные только ради победы памяти было бы
нечестно. Нужны другие задачи, где прошлое знание действительно добавляет
информацию или экономит существенное повторное исследование.

В трёх положительных тройках без provider-сбоя (control01, оба повтора;
control02, первый повтор):

| Вариант | Успех | Native-вызовы | Известные токены контролей | memory.* / skill.load |
| --- | ---: | ---: | ---: | ---: |
| A | 3/3 | 12 | 84626 | 0 / 0 |
| B | 3/3 | 13 | 111423 | 0 / 0 |
| C | 3/3 | 16 | 163202 | 0 / 3 |

Это диагностический срез, **не новая основная оценка**: выбор по отсутствию
provider-сбоя обусловлен исходом и может давать смещение. Стоимость подготовки
здесь не включена; полная стоимость остаётся в отчёте v6. Навык загрузился,
но на этих простых заданиях не сократил число обращений. B здесь вообще не
вызывал memory.search/open: доступность notes не равна их фактическому чтению.

### 2. «Известная ошибка» не стала подтверждённым отрицательным знанием

control03 ожидает подтверждение, что `ready=maybe` не поддерживается. Но recipient
возвращает общий HTTP400; Broker сохраняет `effect_unknown`. Точное последующее
подтверждение отсутствия эффекта тоже не доказывает конкретную причину отказа.
Это намеренно проверяется в `memory_experience_recipient_broker_test.go`.

Следовательно, требовать, чтобы память извлекла из такого прошлого события
проверенный отрицательный урок, некорректно. UNKNOWN нельзя повышать до знания
о причине. Отдельно надо согласовать контракт: `accepted_ready_value` уже
сообщает допустимое значение, тогда как frozen oracle требует текущую реальную
пробу либо прежнее проверенное наблюдение. Следующий набор должен однозначно
различать типизированный отказ по причине и неизвестный эффект.

### 3. Большая часть набора проверяет ограничения, а не накопление знаний

Из восьми случаев 01/02 — повтор и близкий вариант одной простой процедуры;
03 — проблемный отрицательный урок. 04–08 проверяют UNKNOWN, смену окружения,
запрет изменения, область доступа и отзыв источника. Это нужные проверки
безопасности. В 08 независимая note original02 остаётся разрешённой: нельзя
утверждать, что вся память там запрещена.

Нет задач на факты из прошлой сессии, персональные исключения, принятые решения
или продолжение длительной работы. «48 контролей» — это восемь типов по два
повтора и три варианта, а не 48 независимых задач. A означает **без данного
опыта**, а не отключение всей памяти Butler: текущая языковая preference/ProfileStore
подключены во всех вариантах. Спецификация memory-model.md прямо разделяет
Working, Episodic и Profile Memory; этот опыт не охватывает их общую полезность.

### 4. Оценщик не является полноценной проверкой смысла ответа

Выполнены три синтетические подстановки в **саму AST-ветку** неизменённого
`coordinator_assessment.py`, без исполнения её записи файлов:

- control06: инспекция показала false, финал ошибочно говорит true — оценщик
  принимает, поскольку не проверяет финал.
- control04: финал содержит UNKNOWN, но затем без доказательств утверждает
  подтверждённый успех — regex всё равно принимает.
- control01: текущий проверенный артефакт упомянут в ответе с противоположным
  утверждением «НЕ прошёл проверку» — корреляция по идентификатору принимает.

Эти контрпримеры подтверждены [скриптом](audit.py). **Это искусственные ответы,
не обнаруженные ошибки модели в v6.** В просмотренных фактических ответах
control04/06 сохраняются UNKNOWN/failed; оснований переписывать прежние баллы
по этим контрпримерам нет. Положительные финалы целиком на смысл в этом аудите
не переквалифицированы.

Для control03 оценщик вообще всегда ставит false с пометкой «нужно review».
Для имеющихся UNKNOWN это консервативно, но такой оценщик не сможет засчитать
будущий корректный случай без отдельной проверки. Полный frozen oracle содержит
также ограничения области доступа, неизменности и использования источников;
сводный task_success их всех самостоятельно не проверяет. Часть gates проверялась
отдельно, а семантическая независимая квалификация изначально не заявлялась.

### 5. Не изолированы все причины затрат

B/C получают дополнительные инструменты и политику чтения; C также каталог
навыков и инструкции. Это осмысленное сравнение комплекта поведения, но оно не
отделяет пользу содержимого памяти от цены каталогов, инструкций и лишних ходов.
В 13 тройках без control03 и без неизвестного usage все варианты получили
13/13 по прежнему ограниченному оценщику, с 335618/396298/639778 токенами.
Это тоже только условная диагностика; исторические итоги 13/16, 13/16, 14/16
остаются неизменными. Дополнительный успех C совпал со сбоем провайдера у B.

## Что делать следующим

1. **Сначала исправить измерение, без модели.** Сохранить нынешние восемь случаев
   как регрессионный набор интеграции и ограничений. Подготовить отдельный,
   заранее зафиксированный oracle, который отвергает противоречивые ответы,
   различает результат задачи/действия/доставки и умеет принимать настоящий
   подтверждённый отрицательный результат. Проверить его как правильными,
   так и заведомо ложными трассами. Не переоценивать прошлое новым oracle.
2. **Добавить полезность разных типов памяти.** Исторические случайные факты,
   доступные только в прежнем разрешённом источнике; предпочтения с исключениями;
   продолжение работы после новой сессии; сложная повторяемая процедура, которую
   A может заново вывести из тех же текущих данных, но ценой нескольких шагов.
   В recall-задаче честный отказ A — корректная калибровка, хотя задача получения
   факта не выполнена. В каждой семье нужны stale/revoked/distractor/no-benefit
   контроли. Не добавлять в задачу подсказку с самим ответом.
3. **Разделить этапы диагностики.** Проверять запись пригодного факта → наличие
   его среди разрешённых кандидатов → выбор/открытие → применение → текущую
   проверку. Если нужного факта нет в индексе, новая инструкция модели проблему
   не решит. Отдельный контролируемый вариант с поданным правильным фрагментом
   поможет отличить плохой поиск от неспособности использовать найденное; его
   нельзя выдавать за естественную производительность.
4. **Уменьшать цену чтения, а не заставлять читать всё.** Искать при конкретном
   пробеле в знаниях. Возвращать короткое полезное наблюдение/процедуру с областью
   применимости, типом исхода, источником и актуальностью; разворачивать полное
   доказательство по необходимости. UNKNOWN хранить как неизвестный исход.
   Завершать необязательный поиск после отсутствия нового полезного доказательства;
   ограничения доступа, актуальности и журналирования не ослаблять. Недостаток
   evidence не превращать в утверждение успеха. Новые caps в v6 не срабатывали,
   поэтому снижение затрат нельзя объяснять их непосредственным срабатыванием.
5. **Измерять отдачу и окупаемость.** В дополнение к основному A/B/C использовать
   диагностический вариант с одинаковым каталогом/инструкциями и пустой либо
   нерелевантной разрешённой памятью. Считать успех, ложные утверждения, повторные
   ошибки, полезные/бесполезные чтения, tokens, задержку, стоимость создания и
   обслуживания. Разделять холодный запуск и повторное использование. Не обещать
   амортизацию без реального количества повторов; не считать неизвестный usage
   нулём и не выбрасывать provider-сбои из основной оценки.

Это предложения следующего отдельного протокола, **не уже реализованная новая
политика**. PostgreSQL остаётся источником истины, pgvector — поиском,
доступ и исполнение — через Broker; источники не дают полномочий.

## Воспроизводимость и границы

`audit.py` использует только Python stdlib для существующих исследовательских
JSON и AST Python-оценщика; продуктовый код не меняется. Запуск на laba:

```sh
python3 audit.py --root /srv/gitea/butler-acceptance/issue115-native-20261028-v1 \
  --scorer coordinator_assessment.py --out NEW_EXCLUSIVE_DIRECTORY
```

Результат сохранён на laba в `validity-audit-v3/facts.json` и скопирован сюда.
Приватные auth/settings не читаются, сервисы/БД не запускаются, новых модельных
запросов **0**. Raw-архив, прошлые результаты и расходы не изменены. #115 остаётся
не закрытым; этот аудит не является приёмкой целой подсистемы памяти.
