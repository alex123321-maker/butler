# Isolated code workspace store

This kernel storage component implements the file-copy part of issue #17. It is
not a model filesystem tool, shell, runtime sandbox or authorization service.
No production route, Broker handler or container mount is enabled by this delta.
The resource/ownership adapter below is implemented; production exact Broker
action/source/evidence composition and delegated runtime remain required before
product use and issue closure.

`Allocate(Binding)` generates an opaque random workspace ID in the kernel. The
kernel acquires `workspace:<ID>` resource permission, then calls `Create` with
the private `LeaseProof`. Owner/session/task identity and exact task/constraints
revisions are immutable PostgreSQL bindings. Proof fields are excluded from JSON;
model bodies cannot populate them. Run IDs may change across attempts while the
workspace keeps its task binding. A task amendment invalidates old pinned use;
there is no automatic widening or reassignment to the new task revision.

`New` requires a preprovisioned private directory, nonnil guard and fixed limits.
The production Runtime separately holds `LockRoot` for that root's complete
lifetime: Linux directory-inode `flock`, no shared lock/PID/temp file, fixed safe
denial on contention or unsupported platforms. `RootOwner.Check` compares the
held inode and private permissions to the current named directory; `Close`
releases ownership only after the caller drains work. This primitive is separate
from Store authorization and resource arbitration, and writes no PG state.
Lower-level Store/Observer handles do not themselves obtain process ownership;
the owning runtime must keep one RootOwner until all its handles are closed.
`Store.CheckOwner`, `Observer.CheckOwner` and `DeletionRuntime.CheckOwner` compare
their actual opened directory inode with that RootOwner. The runtime validates
all three before returning from startup. A temporary root replacement followed
by restoration of the original named directory cannot validate replacement
handles. The handle comparison and RootOwner's current named-path check are
separate required checks.

The guard checks live ownership, current task/goal/mandate and actual resource
lease/fence/observation version **on the caller's transaction** before workspace
locks. The fixed lock order is ownership → session/task/goal → sorted resources
→ workspace/file observations. The guard repeats the DB-clock check after waits
and immediately before content release/rename. Create/write must take resource
row update locks on the first check; a shared-to-exclusive upgrade between two
writers can deadlock. It must not borrow a completed
run, a second pooled connection, a model-supplied owner or an arbitrary host path.
Read permission, write permission and root-level budget reservations remain the
kernel's responsibility; `CheckTx` is a pure revalidation contract.

`Guard.ConfirmWriteTx(ctx, tx, Access, Snapshot)` is mandatory. After the actual
rename, directory sync and file metadata CAS, it rechecks current authority and
records the new resource observation and consumed write lease on that **same
transaction**, before commit. The production resource adapter calls its owned
`resources.CompleteTx`; it must not defer confirmation or use another connection.
The snapshot is generated by this store, not accepted as a model verdict. A
callback failure after rename retains the pending marker and blocks the copy as
an uncertain effect, even when the PostgreSQL transaction was rolled back.
File version and resource observation version are distinct monotonic counters.

`Guard.ConfirmCreateTx(ctx, tx, Access)` is mandatory too. Creating and syncing
the actual empty namespace is a filesystem effect: its independent observer
records namespace evidence, then consumes the previously committed claim and
advances resource observation on the same workspace metadata transaction. A
synced private pending marker protects this boundary. Post-creation failures
return unknown and keep the claim/marker; they do not invent directory rollback.
After successful Create, the first Write needs a fresh lease at the new resource
version. Create produces no fabricated file snapshot/hash.

`NewResourceGuard(*resources.Store, ResourceAdmission, ResourceEvidence)` requires
all three dependencies. Admission derives live private run/session/task/owner
binding and verifies current exact canonical action/path/body hash, source versions
and shared-budget policy before resource locks, on the caller transaction.
ResourceEvidence independently observes fixed operator storage and writes exact
namespace/file evidence on that transaction. It cannot accept model success.
There is no permissive default or new model/HTTP route.

For create/write the adapter takes resource update locks immediately and requires
the exact live lease to be `claimed`, with its inflight resource marker. Its row
must have been written by a previous transaction; a held lease or accidental
ClaimTx inside the workspace transaction is denied before any filesystem effect.
ClaimTx must be committed by the kernel before calling Create/Write. Confirmations
check current action/source permission, exact actual metadata/observations and
DB time again, then call resources.CompleteTx in this same transaction. No second
pooled connection or completed worker lease is borrowed.

Access.ContentSHA256 is private (`json:"-"`). Write derives it from a copy of the
actual input bytes before the first guard, allowing approved body binding before
rename. Read derives its hash/size from verified current metadata and physical
bytes before the final release check; no caller-supplied hidden read hash is used.

Each workspace contains `tree` and a separate mode-0700 `private/tmp`. No shared
temporary folder, environment, `.git`, credential file or secret reference is
copied. Initial files are staged explicitly through `Write`; the component never
clones an arbitrary repository/directory. Independent copies get independent IDs
and physical files. The same explicit file CAS can merge a reviewed branch patch
into a target copy after the kernel checks its target permission and snapshot.

`Read` returns bounded regular file bytes and `Snapshot{Path,Version,SHA256,Bytes}`.
`Write` requires the exact snapshot; version 0/empty hash means absent. PostgreSQL
workspace locks serialize approved writers across Store instances/processes.
Both version and current physical hash must agree: even a change back to identical
bytes advances the version and does not revive an old plan. The default caps are
1MiB/file, 16MiB/workspace and 256 files. A new file above count/aggregate allowance
is denied before temporary content preparation.

Patched Go 1.27.2 `os.Root` bounds paths. Clean relative paths only; absolute,
traversal, Windows/backslash/colon aliases, symlinks, hardlinked files, nonregular
files and known private credential/temporary names are denied. Private temporary
directories and opened tree identity are checked too. Non-Unix targets currently
fail closed on file link-count proof. Operators must exclude proc/devices,
uncontrolled mounts and external executors with arbitrary filesystem write access.
`os.Root` is not a process sandbox, and this CAS cannot atomically arbitrate an
uncooperative process which ignores Butler and races raw filesystem operations.
Such processes require OS isolation; observed external changes quarantine the copy.
Filename screening is not a universal secret classifier. Source/provenance and
egress checks remain required before importing code or delivering its bytes to a
model; this component imports no credentials and returns no model context itself.

The target file is replaced atomically using a private mode-0600 temporary file,
file sync and target directory sync. PostgreSQL and the filesystem are separate
commit domains. Before rename a synced private marker records only an opaque
attempt ID. An unknown acknowledgement/crash cannot be repaired by assuming hash
equality means authorization: the marker or mismatched physical metadata blocks
the workspace, surviving restart, and `ErrOutcomeUnknown` is never success/replay.
Once both commits are known, removing the marker does not undo the confirmed file
observation. Marker cleanup failure may block future access without inventing an
external rollback. Raw content, paths and credentials never enter that marker.

Quarantine records only a fixed reason and generation in PG. A renewed lease alone
does not clear it. Explicit owner inspection/reconciliation or a separately
reviewed replacement copy must be implemented by the privileged kernel control;
there is intentionally no generic worker unblock API in this component. No model
may change file observations to hide drift. Migration 060 refuses rollback when
workspace history is nonempty.

Reproduce on the isolated lab:

```powershell
pwsh -NoProfile -File scripts/dev/lab.ps1 -Action Sync -RemoteRoot /srv/storage/butler/agents/durable-tasks
ssh laba 'bash /srv/storage/butler/agents/durable-tasks/current/scripts/dev/workspace-lab.sh /srv/storage/butler/agents/durable-tasks'
```

The script starts only its own internal network and disposable PG, uses synthetic
credentials, stores private artifacts below the isolated lab root, runs meaningful
PG/filesystem tests with `-race`, and removes only its containers/network. Pools
have two connections. Tests exercise two real concurrent patches, independent
task copies, ABA/stale snapshots, scopes, expiry during lock wait, stale fencing,
traversal/symlink/hardlink/private-temp aliases, immutable history, aggregate limits,
external edits, failed metadata persistence, failed resource confirmation and a
surviving pending marker. The authority fixture is explicit same-TX PG policy;
its confirmation audit proves the original storage seam. The additional actual
resources.Store/WorkerGuard adapter tests consume real resource leases and record
actual namespace/file observations. Their exact action/evidence policy adapter is
an explicit fixture, not production Broker dispatch or a model verdict. Actual
delegated-tool/runtime tests remain separately pending.

The 2026-10-11 lab proof used source snapshot `20261011-071620-512`, a disposable
PostgreSQL 17 instance and MaxConns=2. All seven top-level tests passed under
`-race`, including resource-confirmation rollback after physical rename. Private
events are retained at
`/srv/storage/butler/agents/durable-tasks/reports/workspace-20261011T001626Z-2480224/tests.jsonl`
with SHA256 `26ce11c4917e29ac70a7512f444122168f404b389898603acc57e34ef5dfc76e`.
This evidence covers the isolated storage contract, not complete issue #17.

Broker/runtime resource tests; it does not supply this workspace's production

`NewObserver` opens its own fixed operator root and independently observes the
actual namespace or file on the confirmation caller's transaction. It grants no
authority and never reads a model verdict. `NamespaceTx` verifies the exact empty
mode-0700 namespace, empty private temporary tree and synced opaque checkpoint.
`FileTx` compares bounded real mode-0600 bytes with the exact owner/session/task/
revision binding and current PostgreSQL file version/hash/length. It checks
opened directory identity and private checkpoint shape again; links, unexpected
private entries and shared permissions cannot become successful evidence.
Observations contain only opaque identity, snapshot metadata and a deterministic
digest, never body, host root, credential or lease. The production admission and
immutable evidence ledger must still call it under their current held locks.

Actual resource-adapter tests now use this observer rather than a test-only
filesystem check. The [observer audit](../../docs/ai/workspace-observer-acceptance.md)
records physical tampering during the real filesystem/PG commit gap, unknown
outcomes, unconsumed claims and blocked/unpublished namespaces. No runtime route,
model capability or deployment flag is enabled by this component.

`DeletionRuntime` is a fixed-root filesystem executor for the owning
[provenance privacy job](../workspaceexec/README.md), not a model tool or recovery
permission. It accepts only a lower-case opaque namespace ID, rejects host paths
and namespace links, erases through os.Root without following links and syncs
the root on both new and idempotent removal. Catalog tombstones and durable job
state are checked by the owner of that job before it calls this executor.
