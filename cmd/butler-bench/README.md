# Бенчмарк Butler

`butler-bench` проверяет механизмы Butler и измеряет, как выбранная модель решает задачи через обычный вход Web. Команда `system` запускает фиксированные тесты продукта. Команда `run` отправляет русскоязычные задания в установленный Butler, сопоставляет ответы с журналами PostgreSQL и сохраняет ход выполнения. Для работы используются Go и уже подключённый в Butler драйвер PostgreSQL.

## Быстрый старт

Выполните команды в PowerShell из корня репозитория.

```powershell
$env:GOCACHE = Join-Path $PWD '.cache/go-build'
$env:GOMODCACHE = Join-Path $PWD '.cache/go-mod'
go build -o .cache/butler-bench.exe ./cmd/butler-bench
& ./.cache/butler-bench.exe list -out .cache/cases.json
& ./.cache/butler-bench.exe system -out .cache/system.json
```

Пути результатов должны быть новыми. Для Linux соберите `go build -o .cache/butler-bench ./cmd/butler-bench`. В `system.json` записываются версия исходников, имена, результаты и длительность каждого обязательного теста. Пропуск, отсутствие ожидаемого теста или ошибка пакета завершают команду с ошибкой.

| Группа | Что считается успехом |
| --- | --- |
| `discovery` | Модель нашла нужный метод по описанию задачи. В фактическом результате `tools.search` есть имя и ссылка на версию контракта. Набор охватывает 96 статических и условных методов. |
| `reasoning` | Извлечение факта, сверка редакций, подсчёт, время, конфиденциальность, распознавание недостатка сведений. Формат и эталон заданы до запуска. |
| `execution` | Загрузка схемы, разбор HTML, извлечение текста, диагностика системы и БД, чтение расписаний. Проверяется результат вызова инструмента. |
| `workflow` | Исправления в нескольких репликах, расчёт по обновлённым данным, сверка двух источников, запись с последующим чтением той же версии файла, жизненный цикл напоминания, открытие оригинала из памяти/уведомлений, проверенный навык и ожидание выбора вкладки. |
| `recipient` | Чтение документа, форма и переходы по каталогу, фильтрация SPA на контрольном сайте. Ответ проверяется по закрытым данным получателя и результатам инструментов. |

`list -group workflow` показывает формулировки и отсутствующие предпосылки. `-cases missing-fact,session-correction` выбирает конкретные задания. Для прогона по умолчанию используется `reasoning`. Идентичность сценария включает его сообщения и критерии оценки. Слова и числа со случайным видом воспроизводятся по `-seed` и номеру повтора. Системный набор отдельно охватывает транспорт, права, сбои, восстановление, бюджеты, жизненный цикл действий и границы расширений.

## Прогон модели

1. Подготовьте отдельный экземпляр Butler с синтетическим владельцем и данными. Используйте сборку Core с поддержкой этого журнала и штатные настройки провайдера, лимитов и цены. Выберите модель в самом Butler. Флаги команды сверяют фактически записанный идентификатор каждого обращения. Для поиска по каталогу нужен включённый `BUTLER_TOOL_DISCOVERY_ENABLED`. Включайте проверяемые возможности и выдавайте обычные полномочия на тестовые ресурсы.
2. Создайте закрытый каталог для оперативного журнала. Передайте его абсолютный путь процессу Core через `BUTLER_BENCH_TRACE_DIR` при старте. В Compose добавьте к сервису `orchestrator` bind mount и эту переменную через лабораторный override. У Core и команды должны быть права на чтение и запись тех же файлов. Путь на хосте передаётся команде через `-trace-dir`. На Windows задайте права каталога через ACL. Каталог результатов, журнал и файл ответа контрольного сайта должны быть вне доступных модели рабочих областей.
3. Укажите в `BUTLER_BENCH_DB` строку подключения к БД этого же стенда. Читателю нужны права SELECT на таблицы приёма, запусков, переходов, сообщений, инструментов, действий, попыток модели, артефактов и доставки. Для защищённой вкладки также нужны таблицы запросов и диспетчеризации выбора. Клиент открывает соединения в режиме read-only. В `-owner-token-file` передаётся локальный файл токена тестового владельца.
4. Создайте `lab.json` с фактической ревизией стенда и SHA-256 общей конфигурации. Зафиксируйте образ, конфигурацию инструментов, общий бюджет, оборудование, часовой пояс и исходное состояние тестовых данных. Удобно вычислить `(Get-FileHash lab-config.json -Algorithm SHA256).Hash.ToLowerInvariant()` для файла, содержащего эти общие параметры. Включайте в этот файл только несекретные значения. Пример формы:

```json
{
  "butler_commit": "<40 hex фактически развёрнутой версии>",
  "environment_sha256": "<64 hex общей конфигурации и исходного состояния>",
  "environment_description": "Изолированный стенд, UTC, один параллельный кандидат",
  "disabled_tools": ["browser.login"]
}
```

Для дополнительных сценариев можно задать `site` с полями `origin, read_code, record_code, spa_url, category, marker`, объекты `memory` и `message` с `query, source_id, code`, а также `skill` с `query, digest, version`. Они относятся к заранее подготовленным оригиналам на стенде. Поле `bindings` сопоставляет ключ вида `wait-for-tab-choice/1` с объектом `{"session":"…","task":"task_…"}`. На каждый повтор выделяется отдельная свежая сессия и задача владельца. Такой привязкой можно снабдить и другие задания, которым нужна задача с полномочиями. Известные выключенные методы перечисляются в `disabled_tools`. При отсутствии заявленной предпосылки слот получает `unavailable` и остаётся в знаменателе. Самостоятельные контрольные сайты описаны в [browser-eval](../browser-eval/README.md) и [browser-spa-eval](../browser-spa-eval/README.md).

```powershell
$bench = (Resolve-Path .cache/butler-bench.exe).Path
$shared = @('-setup','lab.json','-seed','trial-01','-repeat','3','-timeout','4m',
            '-cases','missing-fact,session-correction,parse-selector',
            '-endpoint','http://127.0.0.1:8088','-owner-token-file','private/owner',
            '-trace-dir','private/trace')
& $bench run @shared -provider antigravity -model $modelA -out private/run-a
# Восстановите тот же снимок стенда, переключите модель и проверьте готовность Core.
& $bench run @shared -provider antigravity -model $modelB -out private/run-b
& $bench report -out private/report-a.json private/run-a
& $bench replay -out private/replay-a.json private/run-a
& $bench compare -out private/comparison.json private/run-a private/run-b
```

`$modelA` и `$modelB` — имена реально настроенных моделей. Для полного набора замените `-cases` на `-group all`. Перед каждым кандидатом восстанавливайте одинаковые контрольные данные и состояние бюджета. Для измерения холодного старта и прогретого состояния заведите два отдельных манифеста. Дедлайн задан на весь сценарий. После потери подтверждения доставки команда сохраняет неопределённый исход и останавливает очередь. `report` читает прерванный прогон без повторной отправки.

## Что сохраняется

| Файл | Содержание |
| --- | --- |
| `plan.json`, `cases.json` | Очерёдность, seed, число повторов, лимит, версия кода, среда, модель, платформа команды, исходные сообщения и закрытые критерии. |
| `slot-*.json` | Исход задачи и каждой реплики, задержка клиента, время HTTP-запроса, расходы токенов, имена инструментов, ссылка через имя события на каталог подробностей и хеш его описи. |
| `<событие>/input.json`, `grading.json` | Сообщение владельца, сессия и задача. Снимок, по которому выставлена оценка, содержит текст ответа, подтверждения вызовов и состояние доставки или ожидания согласования. |
| `timeline.json`, `system.jsonl` | Временная шкала БД, состояния, сообщения, предложения и последствия действий, аргументы и результаты инструментов, ошибки, артефакты и доставка. Отдельные интервалы Core показывают подготовку, извлечение памяти и истории, выбор инструментов, сборку запроса и запись контрольных точек. |
| `<хеш операции>.jsonl`, `model-timing.json` | Входные сообщения и схемы на границе Butler и адаптера, продолжения и переданные результаты инструментов, видимые фрагменты ответа и итог, вызовы и аргументы, доступные фазы провайдера, версия модели и сообщённый расход. Для каждого запроса есть длительность и время до первого видимого текста или предложения инструмента. |
| `artifacts.json`, `artifact-*`, `manifest.json` | Индекс продуктов выполнения, сохранённые тексты, структурированные результаты, изображения и вложения при их наличии. Опись содержит размеры и SHA-256 файлов. |

Время на стороне клиента и Core измеряется монотонными часами каждого процесса. Для сопоставления источников записывается UTC, интервалы БД используют сохранённые временные метки. Параллельные и вложенные интервалы могут перекрываться. Время выгрузки измеряется отдельно. Отсутствующая длительность или расход остаются `null`. Журнал включает логические входы и видимый вывод адаптера. Внутреннее состояние провайдера, закрытые рассуждения и необъявленные числа токенов наблюдателю недоступны. Общий и thinking-счётчики сохраняются в событиях, когда их сообщает провайдер. Запросы со stateful-продолжением отмечаются отдельно. Личные идентификаторы авторизации транспорта и заголовки HTTP в этот формат не входят.

`report` и `compare` проверяют сохранённые файлы и точное совпадение с версией протокола. `replay` дополнительно пересчитывает оценки по исходным снимкам, без сети и вызовов модели. Используйте бинарник той же версии для исторического архива. Сохраняйте его вместе с результатами. Контрольные суммы обнаруживают изменения относительно описи и результата слота. Для независимой аттестации храните копию результатов отдельно.

В отчёте есть доля выполненных заданий от запланированных, среднее по группам, успех на всех повторах, парные выигрыши и проигрыши, частоты причин, p50/p95, наблюдаемые запросы и токены. Задания на поиск представлены большой группой, поэтому для оценки целостной работы сравнивайте также `by_group.workflow` и `mean_group_pass_percent`. Инфраструктурные ошибки и неподтверждённая модель остаются отдельными исходами парного сравнения. `result_ready` подтверждает готовую выдачу в Web. Для проверки того, что человек открыл результат, понадобилось бы отдельное подтверждение клиента.

## Сравнение Luna и Terra

Для каждого уровня запустите отдельный Core с `BUTLER_MODEL_PROVIDER=openai`, `BUTLER_OPENAI_MODEL=gpt-6-luna` и `BUTLER_OPENAI_REASONING_EFFORT=low`, `high` или `max`. Передайте тот же уровень в `butler-bench run -effort`. Используйте одинаковые подготовленные копии базы, настройки доступности, порядок, таймаут и задания. Для полного набора передайте `-group all`. Для доступа к методам с областью задачи заранее создайте отдельную задачу владельца и укажите её в `bindings`.

Для Terra укажите `BUTLER_OPENAI_MODEL=gpt-6.1-terra`, `BUTLER_OPENAI_REASONING_EFFORT=medium` и флаги `-model gpt-6.1-terra -effort medium`. В политике бюджета укажите `openai:gpt-6.1-terra`.

Адаптер применяет лимит 8192 выходных токенов и ограничивает ответ одним вызовом инструмента за шаг. В бюджетной политике задайте допустимую стоимость для `openai:gpt-6-luna`. Стоимость резерва в журнале Butler может отличаться от тарифа за фактически использованные и кэшированные токены. При расчёте расходов учитывайте, что OpenAI включает токены рассуждения в выходные.

Бенчмарк сверяет ожидаемые модель и уровень с данными самого OpenAI на каждом завершённом запросе, включая запросы инструментов. `report`, `replay` и `compare` повторяют проверку по сохранённым файлам. Профиль с неподтверждёнными данными получает отдельную ошибку. Предварительные запросы и пробные запуски храните отдельно от сравниваемых серий.

## Проверка самого бенчмарка

В GitHub Actions проверка Butler benchmark запускает системный набор и сквозной контроль на временной БД. Отчёт и архивы синтетических контрольных ответов доступны в артефакте `synthetic-benchmark-results` в течение 14 дней. Полные журналы ваших модельных прогонов сохраняются в выбранном локальном каталоге.

`go test ./cmd/butler-bench ./internal/benchtrace` проверяет каталог, критерии оценивания, сравнение и запись логического транспорта. При `BUTLER_BENCH_TEST_DB` тесты дополнительно используют временную схему в локальной БД `butler_bench_test`. Сквозной контроль использует отдельную пустую PostgreSQL с pgvector, полный комплект миграций, настоящий Web-вход, рабочий процесс и два заданных ответа. Укажите `BUTLER_BENCH_PRODUCT_DB` для этой БД и абсолютный путь `BUTLER_BENCH_TEST_EXECUTABLE`, затем запустите `go test -count=1 -run TestBenchmarkPublicIngressThroughOfflineComparison ./apps/orchestrator/internal/app`. Через `BUTLER_BENCH_FIXTURE_OUTPUT` можно сохранить два контрольных архива в новом каталоге. Их оценки проверяют работу измерителя. Для оценки качества языковых моделей используются прогоны `run` с выбранными провайдерами.

## Тестовый владелец

В модельном прогоне тестовый владелец по умолчанию подтверждает каждый запрос разрешения, привязанный к текущему входу, и ждёт продолжения в той же задаче. Поле `approval_policy` в настройках принимает `approve` или `observe`. Второй вариант позволяет отдельно измерить исход до решения владельца. Для выбора вкладки укажите `fixture_tab_origin` либо используйте адрес контрольного сайта. Стенду нужна тестовая вкладка соответствующего происхождения. Повторное наблюдение одной контрольной точки не отправляет второе решение.

Квитанции с типом, временем, длительностью и HTTP-статусом сохраняются в `owner-decisions.json` внутри доказательств шага. Запрос засвидетельствовать внешний эффект отличается от разрешения на действие. Если результат внешней операции не подтверждён, тестовый владелец сообщает Butler `unknown`. Исход и причина остановки сохраняются в отчёте.

В сценариях чтения сайта учитываются совместимые штатные операции с подтверждённым чтением нужного адреса и кода. Для двух HTML-источников проверяются оба значения, в том числе при одном вызове парсера. Точка после промежуточного «ПРИНЯТО» допускается. В задачах на поиск точного метода сохраняется проверка имени и карточки контракта. Отчёты разных версий протокола нужно интерпретировать с учётом этих условий.
